# 对话式应用：理论与实践

> LLM 的出现让"对话式应用"从"预设选项的菜单树"变成了"自然语言驱动的智能交互"。本文梳理对话式应用的设计框架和架构模式。

---

## 一、对话式应用的核心特点

| 特点 | 传统应用 | LLM 驱动的对话应用 |
| --- | --- | --- |
| 交互方式 | 按钮、菜单、表单 | 自然语言，随口说出需求 |
| 逻辑 | if-else 业务流程 | LLM 推理 + 工具调用 |
| 容错 | 精确匹配，差一个字符就报错 | 语义匹配，容许表达变体 |
| 上下文 | 每步独立，状态靠前端存储 | 多轮对话，模型记住上文 |
| 扩展 | 新功能 = 新代码 | 新能力 = 新 Prompt + 新工具 |

## 二、对话应用的架构分层

```
┌─────────────────────────────────┐
│         用户界面 (UI)            │  ← Streamlit / Gradio / Web Chat
├─────────────────────────────────┤
│         对话管理                 │  ← 多轮记忆、上下文裁剪、历史存储
├─────────────────────────────────┤
│         业务逻辑                 │  ← Prompt 模板 + 工具编排 + 意图路由
├─────────────────────────────────┤
│         LLM Gateway              │  ← 统一 API 入口、路由、Fallback
├─────────────────────────────────┤
│         检索 / 知识层            │  ← RAG：向量库、重排序、文档召回
├─────────────────────────────────┤
│         数据 & 存储              │  ← 对话历史、用户文档、向量数据库
└─────────────────────────────────┘
```

## 三、对话型应用的五步设计法

对应本目录下的五个步骤：

1. **基座模型选型** — 根据任务需求、成本和延迟选模型
2. **参数调整** — Temperature、Top-p、Max Tokens 怎么调
3. **系统提示词设计** — 定义 AI 助手的人格、行为边界和回复风格
4. **示例设计（Few-shot）** — 提供典型对话示例，引导模型按期望方式回答
5. **知识库设计** — 接入 RAG，让模型能基于私有知识回答

这五步是**迭代的**而不是线性的——你在第五步发现检索效果不好，可能需要回到第三步调整 System Prompt。

## 四、多轮对话的状态管理

多轮对话的核心挑战：**模型本身没有"记忆"，需要人工管理对话状态**。

```python
# 最简单的多轮对话：把所有历史消息都带上
conversation = [
    {"role": "system", "content": "你是知识库助手，只能基于给定资料回答"},
    {"role": "user", "content": "什么是 RAG？"},
    {"role": "assistant", "content": "RAG 是检索增强生成...（完整回复）"},
    {"role": "user", "content": "它跟微调有什么区别？"},  # 新问题
]
```

| 策略 | 做法 | 适用场景 |
| --- | --- | --- |
| 全量历史 | 每次把所有历史消息都带上 | 短对话（<10 轮） |
| 滑动窗口 | 只保留最近 N 轮 | 长对话但有上下文窗口限制 |
| 摘要压缩 | 对早期对话做摘要，保留摘要 + 最近几轮 | 需要长期记忆但上下文有限 |
| 向量检索历史 | 把历史对话存入向量库，根据当前问题检索相关历史 | 复杂的多会话场景 |
