# 项目规划与需求分析

> 在写第一行代码之前，先回答清楚三个问题：这个应用要解决什么问题？用户怎么和它交互？技术栈怎么选？

---

## 一、明确项目目标

一个好的 LLM 项目规划从一个具体的场景开始。以"个人知识库问答助手"为例：

**核心价值**：用户上传自己的文档（笔记、合同、论文），助手基于这些文档回答问题。

**项目范围**（MVP）：
1. 用户上传文档 → 向量化 → 构建知识库
2. 用户选择知识库 → 提问 → 检索相关片段 → LLM 生成回答
3. 支持流式输出（打字机效果）
4. 保存历史对话记录

**范围陷阱**：第一版不要做"全局搜索所有知识库""实时更新文档""多用户权限"这类功能——它们会让项目复杂度翻倍。

## 二、用户交互设计

画出用户在界面上的关键操作流程：

```
用户打开应用
  → 上传文档 / 选择已有知识库
  → 输入问题
  → 看到流式回复（逐字输出，不是等全部生成完）
  → 可以追问（多轮对话，助手记住上下文）
  → 查看历史对话
```

## 三、技术架构选型

| 组件 | 常见选择 | 推荐新手方案 | 生产级方案 |
| --- | --- | --- | --- |
| **LLM** | GPT-4o, Claude, 通义千问, DeepSeek | GPT-4o-mini（成本低） | GPT-4o / Claude Sonnet |
| **Embedding** | text-embedding-3, BGE, M3E, 智谱 | text-embedding-3-small | BGE-M3（多语言，开源） |
| **向量数据库** | Chroma, Milvus, Pinecone, Weaviate | Chroma（轻量，零配置） | Milvus（高性能） |
| **文档加载** | LangChain Loaders, LlamaIndex | LangChain（社区文档多） | 自研解析（处理复杂格式） |
| **前端** | Gradio, Streamlit, Next.js | Streamlit（Python 全栈） | Next.js + FastAPI 前后端分离 |
| **编排框架** | LangChain, LlamaIndex, 原生 API | LangChain（教程最多） | 根据场景选或不用框架 |

### 选型决策原则

1. **先跑通，再优化**：第一版用最简单能跑通的技术栈（Chroma + GPT-4o-mini + Streamlit），不要一上来就搞 Milvus 集群
2. **LLM 先选便宜的**：GPT-4o-mini 足够验证大部分场景，等确认产品方向再升级
3. **Embedding 模型不要频繁换**：换了 Embedding 模型就要重建整个向量库——选一个就尽量稳定使用
