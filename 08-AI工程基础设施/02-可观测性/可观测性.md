# 一、概念引入：LLM 应用的可观测性是什么

传统软件开发里，"可观测性（Observability）"解决的是"我在夜里两点收到报警，能不能定位到是哪次请求、哪一行代码出了问题"。到了 LLM 应用时代，情况变得更复杂：应用的行为不再由确定性代码完全决定，而是由模型的**概率输出**决定。同一句话输入同一个模型，今天和明天、甚至同一天不同的 `temperature`，都可能得到内容完全不同的回答。

**可观测性（Observability）** 在 LLM 语境下的含义是：能够回答这三类问题的能力——

1. **好不好**（质量）：回复是否准确、是否幻觉、是否拒绝了不该拒绝的请求。
2. **贵不贵**（成本）：这个功能一天烧了多少 Token、多少钱。
3. **稳不稳**（性能与可靠性）：延迟（TTFT/TPOT）、错误率、缓存命中率，以及下游工具调用是否按预期执行。

更进一步，它还要回答"按可审计性"：这次请求用了哪个模型、哪个提示词版本、温度设了多少、调用链是什么——为排查与合规提供证据链。

> 本目录定位：`08-AI工程基础设施/02-可观测性`，与同目录 `01-K8S与AI`（资源与编排）互补：K8S 管"基础设施活着"，可观测性管"应用是否如预期地活得好"。

# 二、为什么需要：LLM 应用特有的四类痛点

## 2.1 不稳定输出（Non-determinism）

LLM 输出天然具有随机性（温度 > 0 时每次不同）。一个线上功能"上星期还好好的，这星期开始胡说八道"，可能原因包括：提示词模板被某个同事改了一行、模型服务端换了默认参数、外部 API 悄然升级了模型权重、或者是某一个用户输入恰好触发了劣质回复。没有日志和版本追踪，你**根本无法复现**问题。

## 2.2 Token 成本失控

Token 是按量计费的（尤其按 API 服务），请求长度、并发量、模型档位直接换算成账单。一个"prompt 越长、成本越高"的 RAG 应用，如果检索框内容越拼越长，成本会在没有人注意到的角落悄悄翻倍。不可观测 = 成本不可控。

## 2.3 延迟与超时

用户能感受到的延迟分两段：**TTFT（首 token 延迟）** 决定"它接话快不快"，**TPOT（后续每 token 平均时间）× 生成长度** 决定"它说话连贯不连贯"。两者都对体验有决定作用，而它们分别受到上游 API、网络、批处理策略、序列长度的影响——需要分开埋点才能定位。

## 2.4 质量与合规审计

金融、医疗、客服等场景要求"谁、在何时、问了什么、模型回了什么、依据了哪条资料"。此外还要防幻觉（模型编造资料）、防重复、防拒绝不当。没有完整请求日志，审计与评测都无从谈起。

## 2.5 版本迭代风险

生产环境经常冻结或升级模型、提示词、参数。每次升级都可能引入回归（某个提示词模板在新模型下失效）。**把提示词/模型/参数做成可版本化的元数据并随请求埋点**，才能做 A/B 与灰度对比。

# 三、可观测性三大支柱：Logs / Metrics / Traces

这是业界（源自分布式追踪领域，后被 LLM 场景扩展）的公认框架。

## 3.1 Logs 日志

**日志**是**离散事件**的完整记录：一条请求从进入、检索、调用模型、返回，每一关键节点的时间、入参、出参、错误。LLM 场景中最重要的是**请求全链日志**：

- 输入：system prompt、user 消息、检索到的上下文片段。
- 输出：模型完整回复（不截断）。
- 元数据：模型名与版本、提示词模板版本、温度等采样参数、Token 用量、时间戳、用户 ID 与 trace ID。

**特点**：容量大、无固定结构、适合"事后排查"。

## 3.2 Metrics 指标

**指标**是**聚合后的数值**，按固定时间窗滚动计算，用于"实时看大盘、出告警"。核心点：指标是"损失了个体、保留了口径"。

常见指标：

- 请求量 QPS、错误率、P50/P95 延迟。
- Token 相关：输入/输出/累计 token 数、成本估算。
- 专项：缓存命中率、工具调用失败率、内容审核命中率。

**特点**：体积小、适合高频抓取与告警；代表工具 Prometheus + Grafana。

## 3.3 Traces 追踪

**追踪**把一次请求的**多个服务/步骤串成一条链**（Trace / Span），用于回答"慢在哪一步、掉在哪一环"。在 LLM 应用里，链路往往是：

```
用户请求
 └─ 路由/RAG 检索（Span：vector DB 查询耗时）
 ├─ LLM 调用（Span：前置防注入 → 请求模型 → 后处理）
 │  ├─ 工具调用（Span：SQL 查询 / 发邮件 / 调外部 API）
 │  └─ 再次 LLM 调用（Span：根据工具结果总结）
 └─ 响应返回
```

一条 trace 把每个 span 的耗时、入参、出参、错误都串起来，加上 trace ID 就能与日志、指标互相关联（"在 15:00:00 的抛错指标里，点开那条 trace 看完整日志"）。

# 四、LLM 应用特有的观测指标（字典）

| 指标 | 全称 / 定义 | 说明 |
| --- | --- | --- |
| **Token 成本** | 输入+输出 token 数 × 单价 | 按模型档位分别统计，是账单的映射 |
| **TTFT** | Time To First Token，首 token 返回耗时 | 决定"接话快不快"，受网络 + 显存 + 批处理影响 |
| **TPOT** | Time Per Output Token，每输出 token 平均耗时 | 决定生成连贯性；TTFT 已含在内，一段回复总时长 ≈ 输入耗时 + token用数×TPOT |
| **请求成功率** | 200 / 总数，或含重试后的最终成功率 | 区分服务端错误、超时、上游限流 |
| **幻觉率** | 输出与给定资料/上下文不一致的比例 | 需人工或弱化评测标注，抽样评测而非全量 |
| **拒绝率** | 模型对正常请求"拒绝回答"的比例 | 过高说明安全对齐过紧（连"怎么蒸鸡蛋"都拒），过低则威胁违规 |
| **缓存命中率** | 命中 prompt/KV 前缀缓存的请求占比 | 命中率高意味着省 TTFT 与成本；与 vLLM 等前缀缓存联动 |
| **内容审核命中率** | 触发内容安全标记的比例 | 合规风控的晴雨表 |

# 五、关键埋点数据（该记什么）

可观测性最怕"埋了但没用"。建议按如下清单埋点：

1. **输入/输出全文**：完整请求与回复（脱敏后的版本亦可），无截断。
2. **模型标识**：model 名 + 具体版本/快照/权重 commit，_很多事故查到最后是"模型其实被换过了"。
3. **提示词版本**：模板 ID + 版本号 + rendering 后的完整 prompt，_没有它无法复现现象。
4. **采样参数**：temperature、top_p、max_tokens、stop 序列。
5. **Token 与延迟**：prompt_tokens / completion_tokens / total_tokens；TTFT、TPOT、总时长。
6. **调用链**：检索 top-k、工具调用名 + 入参 + 出参 + 状态码；每一步调试信息。
7. **成本维度**：用户 / 会话 / 应用 / 项目 归属；估算成本。
8. **合规元数据**：trace ID、用户 ID、时间戳、鉴权上下文。

> 注意隐私：敏感字段需脱敏（遮蔽身份证/手机号/密钥），否则日志本身就是新的泄露面（呼应 Prompt 安全篇的数据泄露威胁）。

# 六、工具链介绍与对比

## 6.1 Prometheus + Grafana（指标最主流）

- **Prometheus**：时序指标库，Pull 模型拉取指标，内置告警（AlertManager）。
- **Grafana**：可视化大盘，把 Prometheus/Elasticsearch/Loki 等数据源画成仪表盘与告警规则统一管理。
- 定位：**指标**这一柱子的黄金搭档。LLM 应用接入方式通常是：OpenAI 兼容 SDK 的请求在网关层转成指标，或用 prometheus_client 在服务里打点。

## 6.2 OpenTelemetry（统一埋点与导出）

- **OpenTelemetry（OTel）**：W3C 标准的**统一埋点 SDK 与协议**，日志/指标/追踪三合一，一套 SDK 埋点、支持导出到任意后端（Prometheus、Jaeger、Tempo、商业平台）。
- **定位**：是"探测手段"；它自己不带 UI，需要配合后端。LLM 生态里 OTel 有 AI/LLM 语义约定（Semantic Conventions）与 `gen_ai` 命名空间（如 `gen_ai.usage.input_tokens`），正在成为 LLM trace 的工业标准。

## 6.3 LLM 专项观测平台

| 平台 | 定位 | 亮点 | 备注 |
| --- | --- | --- | --- |
| **LangSmith** | LangChain 生态下的排障/评测/回放 | 与 LC/LangGraph 深度绑定，多 span 的 trace 视图 + 数据集评测 | 闭源，有免费额度 |
| **Langfuse** | 开源 LLM 可观测平台 | 自托管、LLM 专属 trace 视图、成本统计、提示词版本管理、评测 | 很喜欢的一句话："LLM 版 Sentry" |
| **Helicone** | LLM API 网关侧代理 | 一行代理即接入，成本/延迟/缓存面板 | 本质是 API 中间层 |
| **Dify 观测** | Dify 平台自带 | 在可视化编排平台内看 trace 与成本 | 与整个 Dify 容器强耦合 |

**选型建议**：

- 指标大盘 → Prometheus + Grafana。
- 只要链路排查 ≈ Langfuse（自托管）或 LangSmith（LC/LC 栈）/ Helicone（只想要便宜便捷）。
- 全栈标准 → OpenTelemetry（埋点）+ 后端选 Prometheus/Grafana/Jaeger 或厂商托管。

# 七、实践：OpenAI 兼容 SDK + Langfuse 接入示例

以 Langfuse（开源、可自托管）为例，演示最典型的做法：**在 Python 代码层给大模型调用包一层观测**。

```bash
# 1. 自托管或云版；本地快速起一个实例
git clone https://github.com/langfuse/langfuse.git
cd langfuse && docker compose up -d
```

```python
# 2. 在应用里配置
import os
from langfuse.client import Langfuse
from openai import OpenAI

langfuse = Langfuse(
    public_key=os.environ["LANGFUSE_PUBLIC_KEY"],
    secret_key=os.environ["LANGFUSE_SECRET_KEY"],
    host=os.environ["LANGFUSE_HOST"],            # 例如 http://localhost:3000
)

client = OpenAI(
    base_url=os.environ.get("OPENAI_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["OPENAI_API_KEY"],
)

# 3. 在关键节点手动埋点（trace + span + generation）
def ask_chat(messages, model="gpt-4o"):
    trace = langfuse.trace(name="chat-qa", input=messages)      # 一条 trace
    span = trace.span(name="llm-call")                           # LLM 调用 span

    resp = client.chat.completions.create(model=model, messages=messages)

    # 把请求/响应/usage 填入观察对象，平台就能画 cost/latency
    span.end(
        output=resp.choices[0].message.content,
        usage={
            "prompt_tokens": resp.usage.prompt_tokens,
            "completion_tokens": resp.usage.completion_tokens,
            "total_tokens": resp.usage.total_tokens,
        },
        model=model, temperature=0.7, max_tokens=1000,
    )
    return resp.choices[0].message.content
```

接入后，Langfuse 的 Dashboard 里就能看到：每条 trace 的 TTFT/总耗时、Token 与预估成本、按模型/按日期的用量曲线、单条请求的输入输出全文回放。**回放是 Langfuse 最实用的能力**：复现一次线上"劣质输出"根本不需要用户配合。

> 若不想改业务代码，可把 Langfuse 作为**网关/代理**夹在 SDK 与服务之间（LLM Gateway 模式），无侵入地完成同等观测，代价是失掉了对应用内部步骤（检索、工具调用）的可见性。

# 八、成本与质量双维监控的实践思路

## 8.1 成本维度

1. **先归一**：把所有模型统一按 `(input_tokens × 单价) + (output_tokens × 单价)` 折算为"估算成本/请求"并打点。
2. **按维度切割**：按用户、会话、功能模块、模型档位分别看成本曲线；设预算告警（如周成本突增 50%）。
3. **拦在源头**：对单用户单日 Token 上限、单请求 max_tokens、RAG 上下文长度做钳制——这同时是对"成本滥用"（见 Prompt 安全篇）的防御。
4. **缓存省成本**：prompt/KV 前缀缓存命中率提升，直接线性降低输入 token 成本（配合 vLLM 前缀缓存）。

## 8.2 质量维度

1. **离线评测集 + 在线抽样**：离线用带答案的评测集在全量或灰度模型上跑准确率；在线对真实请求随机抽样做人工/LLM-as-judge 打分（是否幻觉、是否答非所问）。
2. **反馈链路闭环**：产品里的"有用/无用"按钮 → 转为 label → 回流到观测平台与评测集 → 驱动提示词与模型版本迭代。
3. **把"版本"纳入对比**：同一批线上请求，按模型版本分组看质量分——**迭代决策必须基于数据而不是某一次人工观察**。

**双维同看**：INFO 栏放成本曲线，QUALITY 栏放评分曲线，二者放在一张大盘，"成本降了 30% 但质量分掉了 8 分"一目了然，避免为了省钱而劣化体验，也不至于为感知不到的质量差异多烧钱。

# 九、常见坑与最佳实践

## 常见坑

1. **只埋指标不埋 trace**：出了事只能看到"错误率 5%"，却看不到是哪条链路崩的。三大支柱要一起上。
2. **输出截断就入库**：只存前 200 字符的回复，回放时无法定位幻觉内容。存全文（脱敏后）。
3. **不追踪模型/提示词版本**：线上还是旧模板，你排查半天发现是版本线对不上。版本必须随请求埋点。
4. **敏感数据裸入日志**：手机号、API Key 进日志= 新的泄露面；务必字段级脱敏。
5. **把指标当全部**：Prometheus 能告诉你"P95 爆炸"，但回答不了"那个最慢请求长什么样"——回到 trace。
6. **忽略观测本身的成本**：全埋点 + trace 全开，观测会吃掉不少算力与存储；按比例采样（如 10%）以可控成本换取可操作信息。
7. TTFT/TPOT 混为一谈：优化目标是 TTFT 还是响应总时长策略不同，分开打点。

## 最佳实践清单

- 全链路 trace ID 贯穿：日志、指标、trace 用同一个 ID 关联，出问题一条龙点开。
- 分层采样控制成本：热度普通请求 1%~10% 采样，高价请求该全采的就全采，错误请求 100% 保留。
- 埋点先于上线提测：把观测代码写进 CI 的必测项，避免"上线了才发现没有日志"。
- 告警分级：成本水位、错误率跳变、缓存命中率下降、拒绝率异常——各自独立的告警阈值与值班链路。
- 与评测融合：观测平台的 trace 就是评测的采样池，形成"线上数据 → 评测 → 迭代"闭环。

# 十、小结

1. LLM 应用的不可观测点在于：输出随机、成本与 token 挂钩、延迟分 TTFT/TPOT、质量与合规需要证据链——这是它区别于传统服务必须单独做可观测性的原因。
2. **Logs 回答"发生了什么"、Metrics 回答"大盘怎样"、Traces 回答"链路如何"**，三者统一 trace ID 贯穿。
3. 专属指标多且与成本强相关：Token 成本、TTFT、TPOT、成功/拒绝/幻觉率、缓存命中率。
4. 埋点元数据要有"四件套"：输入输出、模型+提示词版本、采样参数、工具调用链。
5. 工具选型分层：指标用 Prometheus+Grafana；标准埋点用 OpenTelemetry；专项平台按生态选 LangSmith/Langfuse/Helicone/Dify。
6. 双维监控（成本+质量）要同盘对比、闭环迭代；观测自身要控制在可控成本内，先上线再上线前就要埋好。
