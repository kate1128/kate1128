# 模型推理服务：基础设施视角

> 不讨论推理加速的算法原理（那是 `06-模型微调与部署/08-推理加速与部署服务` 的领域），本文关注的是：**在生产环境中，怎么把模型服务搭起来、管起来、让它稳定地对外提供服务**。

---

## 一、推理服务的技术栈选择

LLM 推理不像传统 Web 服务有成熟的标准方案（Nginx + uWSGI + Flask 即可），它有一套专属的技术栈：

| 层 | 常见选择 | 决策要点 |
| --- | --- | --- |
| **推理引擎** | vLLM、TensorRT-LLM、Ollama、llama.cpp、SGLang | 吞吐 vs 延迟、量化需求、易用性 |
| **API 封装** | 原生的 OpenAI 兼容 API（vLLM 自带）、FastAPI 二次封装 | 是否需要自定义认证/限流/日志 |
| **网关/代理** | LiteLLM Proxy、自建 Nginx | 路由、负载均衡、Fallback |
| **编排** | K8s + HPA、Docker Compose | 伸缩策略、GPU 亲和性调度 |
| **监控** | Prometheus + Grafana、Langfuse、自有 callback | 延迟/Token 数/错误率/GPU 利用率 |

## 二、推理引擎选型速查

| 框架 | 核心能力 | 最适合 | 部署复杂度 |
| --- | --- | --- | --- |
| **vLLM** | PagedAttention、Continuous Batching、Tensor Parallelism | 高并发在线推理，生产环境首选 | 中（一条命令启动，调优参数多） |
| **Ollama** | 极致简化，一条命令启动模型 | 本地开发、个人使用、快速实验 | 极低 |
| **TensorRT-LLM** | NVIDIA 官方优化，最高吞吐 | 追求极限性能的 NVIDIA GPU 场景 | 高（需要模型编译） |
| **llama.cpp** | CPU/GPU 混合推理，量化支持好 | 资源受限环境、边缘部署 | 低 |
| **SGLang** | 结构化生成、RadixAttention | 需要复杂输出结构控制 | 中 |

### 选型决策树

```
需要最高吞吐 + 有 NVIDIA GPU? → TensorRT-LLM
需要平衡性能与易用性? → vLLM ⭐ (推荐)
需要快速本地跑一个模型? → Ollama
资源受限 / 用 CPU 跑? → llama.cpp
需要复杂结构化生成? → SGLang
```

## 三、vLLM 生产部署要点

vLLM 是当前最主流的生产级推理引擎。以下是关键部署参数：

```bash
# 单卡启动
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --host 0.0.0.0 --port 8000 \
  --max-model-len 8192 \       # 最大上下文长度
  --gpu-memory-utilization 0.90 \  # GPU 显存占用比例
  --max-num-seqs 256           # 最大并发序列数
```

生产环境关键配置：

| 参数 | 作用 | 建议值 |
| --- | --- | --- |
| `--gpu-memory-utilization` | KV Cache 的显存预算 | 0.85-0.90（留 10% 给 CUDA context 和抖动） |
| `--max-num-seqs` | 最大并发请求数 | 根据显存和模型大小计算 |
| `--max-model-len` | 最大上下文窗口 | 不要无脑设模型上限——它直接影响显存分配 |
| `--tensor-parallel-size` | 多卡并行 | 模型超过单卡显存时使用，设为 GPU 数量 |
| `--enable-prefix-caching` | 前缀缓存 | 开启可显著节省 KV Cache（同 System Prompt 的请求共享） |

## 四、K8s 上的推理服务部署模式

```
┌──────────────────────────────────────────┐
│                  用户请求                  │
└──────────────┬───────────────────────────┘
               │
       ┌───────▼────────┐
       │  LiteLLM Proxy │  ← 统一 API 入口
       │  (路由/限流)    │
       └───────┬────────┘
               │
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐ ┌───▼───┐ ┌───▼───┐
│vLLM   │ │vLLM   │ │vLLM   │  ← 推理实例
│GPU 0  │ │GPU 1  │ │GPU 2  │
└───────┘ └───────┘ └───────┘
```

关键 K8s 配置要点：
- 使用 `nodeSelector` 或 `nodeAffinity` 将推理 Pod 绑定到 GPU 节点
- 通过 HPA 根据 GPU 利用率或请求队列长度自动扩缩
- 使用 `readinessProbe` 确保模型加载完成后再接入流量（vLLM 启动后可能需数分钟加载模型）
