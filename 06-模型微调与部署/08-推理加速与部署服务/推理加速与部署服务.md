# 一、概念引入：推理（Inference）与训练（Training）关注点的根本差异

大模型从训练完成到真正服务用户，中间隔着最后一个关键环节——**推理部署（Inference Serving）**。为什么值得单独开一篇笔记？因为"把模型跑起来"和"把模型训练出来"对系统的要求完全不同：

| 维度 | 训练（Training） | 推理（Inference） |
| --- | --- | --- |
| 核心指标 | **吞吐（Throughput）**：每秒处理多少样本、GPU 利用率 | **延迟（Latency）**：单个请求多久返回、首 token 多久出现 |
| 数据流向 | 大批量、固定形状、走数据并行 | 单个/小批量、长度不断变长、动态到达 |
| 内存特征 | 权重 + 梯度 + 优化器状态，训练中爆炸式增长 | 权重 + 每个请求的 **KV Cache**，随并发与长度膨胀 |
| 对硬件需求 | 关注矩阵吞吐（FLOPS） | 关注**显存带宽**（HBM BW）与串行依赖 |
| 失败容忍 | 可长时间运行、允许断点恢复 | 请求须在可接受时延内返回，不能卡住 |

一句话总结：训练时代追求"算得多、算得满"，推理时代追求"**响应快、并发高、显存省**"。本目录 `06-模型微调与部署/08-推理加速与部署服务` 围绕这两大目标展开。

# 二、为什么需要：自回归解码的瓶颈在哪

## 2.1 逐 token 生成决定了推理是"串行的"

主流 LLM（GPT 系、Llama 系、Qwen 系）都是**自回归（Autoregressive）**模型：每一步只预测一个 token，然后把新 token 拼到已有序列后面，再预测下一个 token。

```
输入："牛顿第一定律是"
生成："牛顿" → "第一" → "定律" → "是" → "物体" → "不受" → ...
      每生成一个 token 都要跑一次完整的前向网络！
```

由此得出三个残酷事实：

- 生成一个长度约 1024 token 的回复，模型要**顺序执行 1024 次前向计算**，中间完全无法并行——第 N 个 token 必须等前 N-1 个生成完。
- 单请求场景 GPU **利用率极低**（论文实测常不足 10%），因为大部分时间模型在"等自己上个输出"，真正的矩阵计算块很小。
- 解码阶段的矩阵运算是**显存带宽受限（Memory-bound）**的，而非算力受限：瓶颈在"把权重和 KV 从 HBM 搬到寄存器"的速度，而不在 FLOPS。

## 2.2 KV Cache：加速的功臣，显存的黑洞

为了让第 N 步不必重算前 N-1 步的 K 和 V，推理框架把每一步算出的键值对缓存下来，这就是 **KV Cache**。

**KV Cache 显存开销估算**（每 token）：

```
每 token KV 显存 = 层数 L × 注意力头数 H × 头维度 D × 2（K、V两份）× 每字段字节数
```

经验参考：一个 7B 模型（约 32 层、隐层 4096、多组注意力）在 FP16 下，**每个 token 约占用 0.5~1 MB 显存**。若 100 个并发请求、每个平均生成 4096 token，KV Cache 合计约 **200~400 GB**，远超单卡 A100（80GB）容量。可见：**推理期显存大头不是权重，而是 KV Cache**。

## 2.3 瓶颈综合症

推理系统面临"四缺"：

1. **缺并行**：自回归的串行 token 依赖，无法直接并行。
2. **缺吞吐**：单个请求批量太小，算力闲置。
3. **缺显存**：KV Cache 随并发数 × 序列长度线性膨胀。
4. **缺带宽**：解码是带宽受限运算，HBM 带宽成天花板。

后文每一项加速技术，都能在上述某一条上"对症下药"。

# 三、加速关键技术（讲透机制）

## 3.1 PagedAttention：分页 KV 缓存（参考 vLLM）

**问题**：传统推理框架为每个请求**预分配一整块连续显存**做 KV Cache，实际使用时序列长度波动很大，于是出现大量"预分配但没用上"的碎片；同时不同请求各自独享缓存，无法复用。

**方案**：vLLM 引入 **PagedAttention**，把 KV Cache 切成固定大小的**块（Block）**，模仿操作系统的**虚拟内存分页（Paging）** 管理：

- 一个请求逻辑上连续的 KV 序列，其物理存储可以是**不连续的多个块**，由块表（Block Table）做映射。
- 按需分配块，需要多少才申请多少，杜绝预分配浪费。
- 多个 prompt 公共前缀的块可以**共享（前缀缓存复用）**，进一步省显存。
- 支持换入换出到 CPU 显存，扩展可用的缓存池。

**效果**：显存利用率大幅提升，同样的卡能承载更多并发、更长的序列，吞吐量也因此显著提升。

## 3.2 Continuous Batching：连续批处理

**静态批处理（Static Batching）**：把 N 个请求一次打包，等 batch 里**所有请求都生成完**才结束批次。短请求生成完只能空等长请求，GPU 大面积空转；batch 一经定死，中途也无法补入新请求。

**连续批处理（Continuous Batching）**：以**每次解码迭代（iteration）**为单位不断调度 batch：

- 每生成一个 token，立即检查 batch：完成的请求移出，腾出的位置立刻塞入新到达的请求。
- batch 内请求可处于不同进度（有人出第 5 个 token，有人出第 50 个 token），只要张量形状一致就能一起算。
- GPU 几乎每个循环都是满的，前后等待被压缩到接近零。

## 3.3 Speculative Decoding：投机采样

**动机**：自回归的串行依赖无法破除，但能不能"一次多猜几个 token 一起验证"？

**机制**（近似解码流派，Golden 等）：

1. 用一个**小/快的草稿模型（Draft Model）**低成本地"猜"出 k 个候选 token。
2. 把 k 个候选 token 连同请求拼在一起，交给**目标大模型一次前向验证**。
3. 验证结果中：前缀连续匹配的 j 个 token 会被接受，直接省掉 j-1 次大模型前向；第一个不匹配的位置之后重新采样。

**要点**：数学上证明该采样分布与原始自回归分布**等价**，不会改变生成质量。典型收益是 1.5~3 倍加速，实际取决于草稿模型与目标模型分布的对齐程度。

## 3.4 量化：FP16 / BF16 / INT8 / INT4

量化把权重（及部分激活）从高精度降到低精度，直接好处是**显存减半、访存减半**——正中带宽受限的痛点；附带还能在部分设备上获得算力收益。

- **FP16**：推理标配，对比 FP32 显存减半且几乎无损。
- **BF16**：与 FP32 同指数位、范围更大，尾数少，**训练与推理通用**；与 FP16 精度差异很小。
- **INT8**：权重 8bit，显存再减半，速度小幅提升，配合**逐层校准**后精度损失基本可控。
- **INT4**：显存降至四分之一（7B 模型约 3.5~4GB），消费级显卡可跑；但**需要校准集做量化，个别任务有明显降质**。

**两大量化方向**：

| 方案 | 思路 | 特点 |
| --- | --- | --- |
| **GPTQ** | 训练后量化，基于二阶近似逐步最小化量化误差 | GPU 友好，效果好；在线流式生成需额外处理 |
| **AWQ** | 按"激活值敏感度"选择保护 1% 关键权重通道 | 激活感知，被 vLLM/Ollama/TGI 广泛内置 |

> 量化的其他话题（剪枝、蒸馏、感知训练）可参考本知识库 `04-模型量化与压缩` 目录。量化不是唯一解，它和 PagedAttention 等手段是**叠加关系**，生产上往往同时使用。

# 四、框架横向对比表

| 框架 | 主打亮点 | 适用场景 | 说明 |
| --- | --- | --- | --- |
| **vLLM** | PagedAttention + Continuous Batching，吞吐领先 | 高并发在线服务、OpenAI 兼容 API | 生态最活跃，支持多卡、前缀缓存、量化 |
| **SGLang** | RadixAttention 前缀树缓存，结构化输出加速 | 复杂推理链、需要高效前缀复用（多轮对话 / Agent） | 近年性能爬升很快 |
| **HuggingFace TGI** | 与 HF 生态无缝、易用、支持推测解码 | 中小团队快速上线、研究原型 | 接入最省事，性能略逊 vLLM |
| **TensorRT-LLM** | NVIDIA 官方、算子级极致优化（CUDA Graph） | 追求单机极致的生产环境 | 需要掌握 TRT 构建，复杂度高 |
| **llama.cpp** | 纯 C++ 无依赖、GGUF 量化成熟 | CPU / 消费级 / 边缘设备 | 跨平台，性能有限但零依赖 |

选型口诀：**要吞吐并发选 vLLM；要复杂 Agent/前缀复用选 SGLang；要最省事选 TGI；要极致的单卡性能投 TensorRT-LLM；要边缘/CPU 走 llama.cpp。**

# 五、部署实践：vLLM 启动 OpenAI 兼容服务

## 5.1 启动命令

```bash
# 安装
pip install vllm

# 启动 OpenAI 兼容的异步推理服务，监听 8000 端口
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --tensor-parallel-size 1 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.9 \
    --dtype float16
```

参数说明：

- `--tensor-parallel-size 1`：单卡；多卡时设为卡数，同机多卡以张量并行切分权重。
- `--max-model-len 8192`：限制最大序列长度，直接决定 KV Cache 预算，是显存安全阀。
- `--gpu-memory-utilization 0.9`：允许系统使用 90% GPU 显存（默认 0.9）。
- `--dtype float16`：推理精度，可改 `bfloat16`。

## 5.2 Python 客户端调用（OpenAI 兼容接口）

vLLM 暴露的接口与 OpenAI API 兼容，任意 OpenAI SDK 改一下 `base_url` 即可：

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",   # 本地 vLLM 服务
    api_key="EMPTY",                        # 本地服务无需真实密钥
)

resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[
        {"role": "system", "content": "你是一位耐心的编程助教。"},
        {"role": "user", "content": "请用通俗的语言解释什么是 KV Cache。"},
    ],
    temperature=0.7,
    max_tokens=512,
)

print(resp.choices[0].message.content)
```

## 5.3 与原样 HF transformers 推理的对比

**原生 HF 做法（研究与对照用，不推荐生产）**：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct", torch_dtype=torch.float16
).cuda().eval()

prompt = tok.apply_chat_template(
    [{"role": "user", "content": "请用一句话介绍 vLLM。"}],
    add_generation_prompt=True,
)
inputs = tok(prompt, return_tensors="pt").to("cuda")
out = model.generate(**inputs, max_new_tokens=512)
print(tok.decode(out[0][len(inputs["input_ids"][0]):], skip_special_tokens=True))
```

**对比要点**：

| 项目 | 原生 HF | vLLM |
| --- | --- | --- |
| 并发处理 | 需自己手动组 batch 调度 | 内置 Continuous Batching 自动调度 |
| KV Cache 管理 | 每请求固定预分配，碎片严重 | PagedAttention 分页按需分配 |
| 官方基准吞吐（同卡同模型） | 1×（基线） | 通常 5~30 倍（并发场景） |
| 额外依赖 | 极少 | 需与 CUDA/PyTorch 版本匹配 |

生产不建议裸跑 HF：即使单用户聊天，vLLM 在显存开销与延迟上也明显占优。

# 六、容量规划：显存 / 并发 / 吞吐的粗略估算

**显存估算三步**：

1. **权重**：参数量 × 每参数字节。7B FP16 ≈ 14GB；7B INT4 ≈ 3.5GB。
2. **推理态显存（主要是 KV Cache）** = 每 token KV 字节 × 平均生成长度 × 并发数。
3. **预留**：CUDA 上下文、激活中间量、框架自身约 2~4GB。

**粗估公式**：

```
总显存 ≈ 权重显存 + (每token KV字节 × 平均生成长度 × 并发数) + 预留
理论并发上限 ≈ max(硬件显存 - 权重 - 预留, 0) ÷ (每token KV字节 × 平均生成长度)
```

**经验值**（7B/FP16 思路）：

- 单卡 A100 80GB：约 8~20 并发（取决于平均生成长度与对话轮次）。
- 单卡 4090 24GB：4~8 并发，需配合 INT4 或收紧 `--max-model-len`。
- 吞吐数量级：vLLM 在 A100 上跑 7B，常见 100~300 token/s 级别的服务级吞吐。

> 细算用框架自带的压测工具（如 vLLM 的 `benchmark_serving.py`）实测，以"并发 × prompt 长度 × 生成长度"为输入，远比脑算靠谱。

# 八、常见坑

1. **KV Cache 估算错误**：只按"7B 模型 = 14GB 权重"算显存，忽略 KV Cache，结果 OOM。务必把 `--max-model-len` 与人手估计的并发数代入公式。
2. **用单请求时序衡量平台**：只看"一次生成的秒数"，没看"端到端吞吐（token/s/卡）"。正确姿势是用并发压测工具。
3. **没有 warmup 就压测**：首次加载权重、CUDA 图构建的开销会被计入首请求延迟，压测前先发几个请求暖机。
4. **量化后只看单句输出**：INT4 降质是统计性的，要用任务级评测（如 MMLU、真实下游指标）对拍，而不是对比一两句话。
5. **忽略网络与前到远延迟**：用户感知到的"慢"往往是网络 RTT + 生成长时间（TPOT × 长度），而不是框架开销。
6. **长请求导致显存碎片累积**：连续跑高并发长序列后，可能出现"显存没满却 OOM"，PagedAttention（及内存换入换出）正是对应解法。
7. **版本强绑定**：vLLM 与 PyTorch/CUDA 版本强绑定，升级前先看配套矩阵，部署到 CI 里做回归。

# 九、小结

1. 推理与训练关注点相反：训练求吞吐走大 batch，推理求**低延迟 + 高并发 + 省显存**。
2. 自回归串行依赖与 KV Cache 膨胀是推理性能的真正瓶颈，"四缺"是理解一切加速技术的钥匙。
3. 四大加速方案各治一症：**PagedAttention** 治显存碎片、**Continuous Batching** 治 GPU 空转、**投机采样** 治串行瓶颈、**量化** 治带宽与显存压力。
4. 生产优先 vLLM / SGLang（OpenAI 兼容、内置调度），边缘与 CPU 走 llama.cpp，单卡极致选 TensorRT-LLM。
5. 容量规划用"权重 + KV Cache + 预留"公式粗估，再用基准工具实测校准；部署时盯住 KV 预算、warmup 与版本匹配。
