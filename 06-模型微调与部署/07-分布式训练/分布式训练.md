# 分布式训练（Distributed Training）

> 本笔记定位：深度学完"训练的最后一公里"——单卡装不下、单卡算不完时怎么办。把数据并行 / 模型并行 / 流水线并行 / ZeRO / FSDP / 混合精度 / 通信原语一次讲透，最后给出可运行的 torchrun DDP 和 FSDP 示例。适合在跑大模型 SFT/RLHF 之前通读。

## 一、概念引入：什么是分布式训练

**分布式训练**就是把一次模型的训练任务，拆到多张 GPU（可以在一台机器上叫"单机多卡"，也可以跨多台机器叫"多机多卡"）上并行完成，并保证最终效果（在数值上）和单卡训练基本等价。它不是一个"要不要"的锦上添花，而是现代大模型训练的**必经之路**——LLaMA-7B 光 FP16 权重就 14GB，加上 Adam 优化器状态，单卡 80GB 的 A100 都勉强；而 GPT-3（1750 亿参数）需要上千张 GPU 训练数月。

## 二、为什么需要分布式：单卡的显存与算力瓶颈

1. **显存（VRAM）瓶颈**：一个模型要训练，显存里至少要同时装得下：参数本身（FP32 权重/FP16 权重）、gradient（和权重同尺寸）、优化器状态（Adam 需要两份动量，约 2 倍参数）、中间激活值（batch 相关）这几大类。粗略估算法：**训练显存 ≈ 参数大小 × 16~20（FP16 + Adam）+ 激活值**。70B 的模型仅参数+梯度+优化器三项就超过 500GB，而单卡最多几百 GB，分布式势在必行。
2. **算力瓶颈**：单卡算力有限，训练一个 7B 模型完整跑一遍可能要几周；千卡并行后时间可压缩到几天。分布式本质是"分摊显存 + 倍增算力"，用通信开销换训练时间。

## 三、四大并行策略：把饼切开的方法

并行策略回答的是同一个问题：**一块饼（模型的参数量 + 数据）怎么切到 N 张卡上**。按"切什么"分四种。

### 3.1 数据并行 DP / DDP（Data Parallel）

- **思路**：每张卡都放一份完整的模型副本，只把训练数据切成 N 份，每卡训练自己的子批。每轮结束各卡把自己的梯度汇总（All-Reduce）得到全局梯度，再用它同步更新所有卡上的参数副本。
- **DP vs DDP**：PyTorch 早期 `DataParallel`（DP）是单进程多线程模型，主卡负责梯度归约、有负载不均和通信瓶颈；`DistributedDataParallel`（DDP）是多进程，每卡一个独立进程，梯度 All-Reduce 用 ring-allreduce，均衡高效，**训练场景一律用 DDP**。
- **特征**：**不省显存**（每卡都要全套参数），只省时间；卡越多单批次越多全局 batch 越大，训练收敛更快。
- **适用**：模型单卡装得下、想提速。

### 3.2 张量并行 TP（Tensor / Model Parallel）

- **思路**：把**单个矩阵（层内的权重）沿维度切开**，分到多张卡上。典型例子：Transformer 的 Attention Q/K/V 投影和 FFN 的两个线性层，每张卡只算自己的"片"，最后把结果拼接起来。Megatron-LM 用的就是 1D 行/列切分。
- **特征**：每张卡只有部分参数，**省显存**（配合数据并行可把模型切到千卡）；但因为是层内拆分，前向/反向每一步都需要卡间通信（一次 all-gather/reduce-scatter），**通信非常密集**，通常要求卡间用高速网（NVLink/InfiniBand）紧耦合。
- **适用**：单卡放不下的超大模型；对通信速度要求高，一般"节点内"（同一台机器）用 TP，跨节点少用。

### 3.3 流水线并行 PP（Pipeline Parallel）

- **思路**：把模型**按层切成若干段**，每张卡负责其中一段（如 Layer 0-7 在卡 A，8-15 在卡 B）。数据像流水线一样一段段往后传——第 1 批数据在卡代校验算第 1 段时，第 2 批数据同时进入卡 A 的第 1 段，卡间按序接力。
- **特征**：**省显存**，单位时间同时激活的层少；但也带来"流水线气泡"（bubble）——切得越多、气泡越大，利用率下降；还要处理中段层的梯度要和前段层交换（需要切一部分梯度裁剪/梯度同步的细节）。
- **适用**：模型纵向很深、单卡容纳不下完整模型的情况，是 TP 在大规模集群上的重要补充。

### 3.4 ZeRO：分区优化器状态/梯度/参数（把"数据并行"升级）

ZeRO 是 DeepSpeed 提出的"**挖掉数据并行里的冗余**"方法。数据并行最大的浪费是：N 张卡存了 N 份完整参数 + N 份完整梯度 + N 份完整优化器状态，这些在每轮其实几乎一样。ZeRO 按阶段逐步把这些"用不到的部分"切分到所有卡上：

| ZeRO 阶段 | 切分对象 | 省下的显存 |
| --- | --- | --- |
| Stage 1 | 优化器状态（Adam 的 m、v，最大头）按卡切分 | 至少减掉优化器状态这块大头 |
| Stage 2 | 优化器状态 + **梯度**按卡切分，计算完即丢弃本卡不需要的梯度 | 梯度这块也省下 |
| Stage 3 | 优化器状态 + 梯度 + **参数**全部按卡切分，用到哪层才把该层参数从别的卡取回（分区权重） | 参数也能分到多卡，显存近似"除以卡数" |

它的核心技巧是**通信换显存**：Stage 3 每次前向需要"weight gather"（从别的卡临时取回参数），每次反向需要"reduce-scatter"梯度，"partition optimizer"存各自片再 all-gather 更新。肉眼可见省出超大模型训练的整片天空——Stage 3 让几十 B 的模型也能在不大集群上开训。

### 3.5 FSDP 与 ZeRO 的关系

**FSDP（Fully Sharded Data Parallel）**是 PyTorch 官方对标 ZeRO-3 的实现，二者是"一个思想、两种实现"：

- FSDP = **数据并行的含义 + ZeRO Stage3 的参数分片**。每张卡只持有模型参数的分片，需要时"拉取"当前层参数（拉全部或只拉分片），算完即放。
- **自动分片策略**：`sharding_strategy` 可设 `FULL_SHARD`（全部切 = ZeRO-3）、`SHARD_GRAD_OP`（只切梯度=ZeRO-2）、`NO_SHARD`（= DDP）。
- **嵌套**：FSDP/ZeRO 可以和 TP、PP 组合。ZeRO 负责"参数的存储分片"，TP 负责"每次计算的分片"，业界标准组合是 PP(层间) + TP(层内) + ZeRO(参数存储) 三明治。
- DeepSpeed 中有 `deepspeed_config` 的 `zero_optimization`；PyTorch 用 `torch.distributed.fsdp.FullyShardedDataParallel`。选 DeepSpeed 更省标配（ZeRO 支持 offload CPU），选 FSDP 更贴近官方生态。

### 3.6 四大策略速查表

| 策略 | 切什么 | 省显存 | 通信频率 | 典型场景 |
| --- | --- | --- | --- | --- |
| DDP | 数据 | 不省 | 每轮一次 All-Reduce | 单卡装得下、提升吞吐 |
| TP | 层内权重 | 省 | 每步多次 | 超大模型，NVLink 节点内 |
| PP | 层间 | 省 | 每步少量(段间) | 模型很深、纵向切 |
| ZeRO-3 / FSDP | 优化器/梯度/参数 | 省(最大) | gather/scatter 换显存 | 单卡放不下，标配方案 |

## 四、混合精度训练：用 FP16/BF16 省一半显存再加倍算力

现代 GPU 对 FP16/BF16 有专门的高吞吐计算单元（如 A100 FP16 算力为 FP32 的 2 倍），且占显存只有 FP32 的一半，于是有了"混合精度"：

- **FP16（半精度）**：节省显存、快；但表示范围小，梯度过小会下溢成 0，过大溢出成 inf。
- **BF16（Brain Float16）**：谷歌提出的，指数位和 FP32 一样，范围大**不会溢出**，训练稳定，天生适合大模型，H100/A100 都原生支持；缺点是尾数精度略低。
- **梯度缩放（Gradient Scaling）**：解决 FP16 下溢问题的关键机制：反向传播前把 loss 乘一个大数（如 `loss *= 65536`），梯度也整体放大再存入 FP16；更新前再除回来，等于"给梯度抬升到不丢精度的档位沟通"（`optimizer.step` 前 `scaler.step`，若梯度 inf 再降 scale 重试）。实现上有 `torch.cuda.amp.GradScaler` 自动完成。

```python
# PyTorch 官方自动混合精度最小流程（伪代码）
scaler = torch.cuda.amp.GradScaler()
for batch in loader:
    with torch.autocast(device_type="cuda", dtype=torch.float16):   # 前向/loss 用低精度
        loss = loss_fn(model(batch))
    scaler.scale(loss).backward()          # 缩放梯度再反向
    scaler.step(optimizer)                 # 未缩放就更新 → 内部除回尺度
    scaler.update()                        # 依据 inf/NaN 动态调整 scale
    optimizer.zero_grad()
```

## 五、通信原语与通信瓶颈：分布式的心脏

分布式训练绕不开"卡与卡之间同步"，核心通信集合操作（Collective Communication，底层由 NCCL 提供）：

| 原语 | 作用 | 数据示意 |
| --- | --- | --- |
| All-Reduce | 所有卡把自己的张量加起来，再**分发给所有卡** | 每卡给一份，各卡得全局和 |
| Reduce-Scatter | 所有卡加总后，**每卡只保留自己的那一片** | 用于梯度分片（ZeRO） |
| All-Gather | 每卡有不同片，**收集成完整张量给每卡** | 用于参数/权重取回（FSDP） |
| Broadcast | 把一张卡的张量广播给所有卡 | 启动时同步权重 |

**通信瓶颈与计算/通信比**：GPU 算得越快，通信占的时间占比越大。衡量指标常用 **计算/通信比（compute-to-communication ratio）= 计算量 / 通信量**。比值高说明算得多传得少（好），比值低说明卡大多在等通信（差）。DDP 每轮一次 All-Reduce 通信量=梯度的 2 倍，通信量和参数量成正比，所以模型越大通信越重；ZeRO 用 reduce-scatter+gather 把单次通信量分摊、从而缓解带宽压力。降低通信占比的手段：增大 batch（计算量更大）、梯度压缩、梯度异步、overlap（通信和计算重叠）。

## 六、DeepSpeed 用法：ZeRO Stage 配置示例

## 七、PyTorch 实践：torchrun DDP + FSDP 简例

### 7.1 一段自带的完整示例：DDP 训练一个 2 层 MLP（单机多卡任选卡数）

```python
# ddp_example.py
import os, torch, torch.distributed as dist, torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP

def get_rank():
    return int(os.environ["RANK"])          # torchrun 会注入 RANK / LOCAL_RANK / WORLD_SIZE

def main():
    dist.init_process_group("nccl")          # 初始化进程组（自动读取 MASTER_ADDR 等环境变量）
    rank, local_rank, world = get_rank(), int(os.environ["LOCAL_RANK"]), int(os.environ["WORLD_SIZE"])
    torch.cuda.set_device(local_rank)

    # 每卡同类数据切片
    dataset = torch.randn(world * 8, 8)      # 简单假数据：按 world 切
    my_data = dataset.split(8)[rank].cuda(local_rank)
    labels = torch.zeros(world * 8, 1).split(8)[rank].cuda(local_rank)

    # 数据并行：同一份模型拷贝到每卡，包 DDP
    model = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 1)).cuda(local_rank)
    model = DDP(model, device_ids=[local_rank])   # DDP 内部自动处理梯度 All-Reduce

    opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
    mse = nn.MSELoss()
    for step in range(50):
        opt.zero_grad()
        loss = mse(model(my_data), labels)
        loss.backward()                      # 每卡各自算梯度 → DDP 同步归约 → 大家一致的梯度
        opt.step()                          # 每卡同一步、同样的梯度 → 参数保持一致
        if rank == 0 and step % 10 == 0:     # 只在主进程打印，避免刷屏
            print(f"step {step} loss {loss.item():.4f} world={world}")
    dist.barrier()                           # 同步等待所有卡完成
    dist.destroy_process_group()

if __name__ == "__main__":
    main()
```

### 7.2 启动命令（关键！torchrun 是官方标准入口）

```bash
# 单机 4 卡
torchrun --nproc_per_node=4 --master_port=29500 ddp_example.py

# 多机（2 台机器 × 每台 8 卡）：每台机器分别运行相同命令，换 MASTER_ADDR
# 节点 1: torchrun --nnodes=2 --nproc_per_node=8 --rdzv_endpoint=10.0.0.1:29500 ddp_example.py
# 节点 2: torchrun --nnodes=2 --nproc_per_node=8 --rdzv_endpoint=10.0.0.1:29500 ddp_example.py
```

说明：`--nproc_per_node` 单机卡数；`--nnodes` 机器数，多机必须就 1 台指定为 rendezvous 端点（`--rdzv_endpoint=主节点IP:端口`）；`RANK`（全局序号）/`LOCAL_RANK`（本机序号）/`WORLD_SIZE`（总卡数）由 torchrun 自动注入代码读取。

## 八、训练资源测算：显存怎么估

工程上从"参数个数 + 精度 + 优化器 + batch"四块粗算（单卡训练，单位字节）：

```
显存占用 ≈ 参数 × 精度 + 梯度 × 精度 + 优化器状态 + 激活值
以 7B 模型 FP16 + Adam 混精为例（约数）：
  参数 7B × 2B = 14GB（FP16）
  梯度 7B × 2B = 14GB
  Adam 状态 7B × 4B × 2 = 56GB（m、v 各 FP32）
  合计 ≈ 84GB + 激活值（跟 batch×seq_len 成正比）
```

所以：7B 模型其实 **单卡 80GB（A100/H100）都超**，必须 ZeRO/FSDP 或 QLoRA（4bit 量化）压到 8~10GB 内跑；而 **推理（只有权重+KV cache）大约只要 ~15GB**。给个经验：**训练显存 ≈ 推理权重的 6~8 倍**（FP16+Adam）。反向推算：先量推理权重大小（参数量×2B），再决定是否进分布式。

## 九、常见坑

1. **卡间通信失败 / NCCL 报错**：常见于端口被占、`MASTER_ADDR` 配错、驱动/网卡驱动不匹配、防火墙没放行。先查环境变量（`RANK`/`LOCAL_RANK`/`MASTER_ADDR`/`MASTER_PORT`），`--master_port` 换一个没被占的端口。
2. **OOM（显存不足）**：优先减 `batch_size`、开 `torch.cuda.amp`、`gradient_checkpointing`（激活值重算）、或从 DDP 换 ZeRO-2/FSDP；别傻乎乎靠机器换大显存。
3. **负载不均**：数据并行里有些卡拿到样本难些（或各卡 batch 数不整除），耗时钉在最慢的卡上；用 `DistributedSampler` 保证每卡等量，且用层数均匀的 PP。
4. **BN（BatchNorm）同步问题**：DDP 里默认每卡各算各的 batch 统计量，小 batch 卡会不准；需要跨卡同步统计时要开 `DDP(broadcast_buffers=True)` 或改用 SyncBatchNorm——不过大模型基本用 LayerNorm，天然不受影响。
5. **seed 不一致**：多机多卡记得 `seed = base + rank`，否则各卡数据顺序不同，训练发散。
6. **忘了 `dist.barrier()`**（多卡校验/保存模型切片前）：日志乱序、保存的模型不完整，加 barrier。保存用主卡保存、或每卡存自己的分片再汇聚。
7. **多机跑不通先回单机**：把 `--nnodes` 改 1 验证代码正确性，再逐步加节点，降低排查面。

## 十、小结与本库衔接

一张图收尾：**单卡装不下 → 上 ZeRO/FSDP 分片参数 + 混合精度省一半；单卡算不动 → 上 DDP 并行数据提吞吐；模型实在横跨千卡 → 再叠 TP+PP。通信是代价，显存是收益，算清楚自己的 GPU 和带宽再选组合。**

衔接关系：本库 `01-微调`/`02-参数高效微调PEFT` 中的 LoRA/QLoRA 正是不动大参数的省显存手段，与本文 ZeRO 是"显存优化两个正交方向"（拆参数 vs 少训参数），两者配合（QLoRA + ZeRO-offload）可以在最低配置下训最大模型；`04-模型量化与压缩` 进一步压缩推理显存；做完训练用 `08-推理加速与部署服务`（vLLM/TensorRT-LLM）上生产。深度学习地基部分（梯度反向传播、优化器）见本库 `01-大模型基础/03-深度学习基础`。
