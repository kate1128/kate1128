# 多智能体协作（Multi-Agent Collaboration）

## 一、概念引入：从单 Agent 到多 Agent

我们前面学习的 LangChain Agent、CrewAI 单 Agent 等，本质上都是一个"思考-行动"闭环：大模型作为大脑，配合规划（Planning）、记忆（Memory）、工具（Tools）、行动（Action）四大要素去完成任务。单个 Agent 在一个任务中扮演"全能选手"，所有规划、工具调用、答案生成都由同一个模型上下文承担。

但现实世界的复杂任务往往涉及多个专业领域：例如"做一个产品市场分析报告"，既要查数据、又要做竞品分析、还要写文案排版。把所有这些塞进一个 Agent、塞进一个上下文窗口，会出现明显瓶颈。于是"多智能体协作（Multi-Agent Collaboration）"的概念被提出：把一个复杂任务拆解为多个子任务，交给多个各司其职的 Agent 去执行，并通过一定的协作机制让它们相互配合、汇聚出最终结果。

## 二、为什么需要多智能体：单 Agent 的局限

先分析单 Agent 的四个核心局限，这也就是多智能体的动机来源：

- **上下文窗口瓶颈**：复杂任务需要大量中间过程信息，单 Agent 很容易把上下文塞爆，导致"中间忘了前面在干什么"，出现幻觉或自相矛盾。
- **角色冲突与质量不稳**：同一个模型既做"头脑风暴者"又做"批评者"，很难既发散又收敛。研究发现，让模型扮演专家或批评者时，明确的角色分工能显著提升输出质量，因为模型可以专心地沿一个角色"演"。
- **串行效率低**：多步骤任务在单 Agent 内部是串行推理，无法并行处理独立子任务；而多 Agent 可以把彼此无依赖的子任务交给不同 Agent 并行执行。
- **无自我纠错机制**：单 Agent 的"反思"往往是自说自话，缺乏外部校验者。多个 Agent 互评、辩论，相当于引入了一个"外部客观视角"，能有效发现逻辑漏洞。

## 三、核心原理与架构：五种主流协作模式

多智能体系统的核心问题是"Agent 之间如何组织、如何通信"。下面拆解五种主流架构模式，配合文字示意图说明流程。

### 3.1 编排者模式（Orchestrator-Workers）

这是一种"中央集权"模式。中央有一个 Orchestrator（编排者/队长）Agent 负责接收总任务、拆解子任务、分派给 Worker（工人）Agent、收拢结果并做总结。Worker 之间不直接通信，只与 Orchestrator 交互。

```
用户请求
   │
   ▼
[ Orchestrator ] ──拆解──► [ Worker A（查资料） ]
   ▲  │                        │
   │  │◄───────返回结果────────┘
   │  │
   │  ├─► [ Worker B（写代码） ]  （可与 A 并行）
   │  │          │
   │  └───────返回结果───────────┘
   │
 [ 汇总、整合、产出最终答案 ] ──► 用户
```

OpenAI 2025 年在《Introducing AgentKit》中明确把 Orchestrator-Workers 命名为 Agentic Loop 的一种参考实现（对应 AgentKit 的 Orchestrator-Workers 流程）。它的优点是结构清晰、可控性强、扩缩容容易（加 Worker 即可）；缺点是中央 Orchestrator 是单点，容易成为性能与可靠性瓶颈，且 Orchestrator 的理解能力决定了全系统上限。

### 3.2 协商模式（Negotiation）

多个 Agent 地位平等，为了达成某个共同目标（如确定一个方案、签订一个虚拟合约），各 Agent 先各自提出方案，然后互相协商、让步、修改，直到收敛或达到最大轮数。消息每次广播给全体或定向发给某几个 Agent。

```
[ Agent A（提方案1） ]
   ↕  消息来回
[ Agent B（提方案2） ]   ──► 各自迭代优化方案 ──► 收敛出最终方案
   ↕
[ Agent C（质疑/提方的第三方） ]
```

典型代表是 CAMEL 框架（Communicative Agents）里两个 Agent 互相抛问题、解决问题、交替推进任务。协商模式适合需要"多方取舍"的决策类任务，但由于可能无限循环，通常需要设定最大协商轮数做硬性兜底。

### 3.3 辩论模式（Debate）

让多个 Agent 扮演不同立场，各自就同一问题给出答案和论证，然后互相阅读对方的论证、再修正自己的回答，经过多轮迭代提高正确率。本质上是把模型的"自我批判"扩展为"多人互批"。

```
轮次1  轮次2  轮次3
 A1 ──► A1' ──► A1''   （A 看 B、C 的论证后修改）
 B1 ──► B1' ──► B1''   （自由辩论）
 C1 ──► C1' ──► C1''   （多轮直至收敛/投票）
```

Multi-Agent Debate（MAD）论文是这一方向的代表作：几个 LLM 就同一问题展开多轮辩论，数学推理与事实问答的正确率显著高于单模型。适合高正确性要求的场景，但 Token 消耗会成倍放大。

### 3.4 层级模式（Hierarchy）

存在多层管理关系：高级 Agent 管理中级 Agent，中级管理低级。信息在各层之间纵向传递，横向一般不做通信。常见于任务粒度差异大的场景（如公司组织架构模拟：CEO → 部门主管 → 员工）。

```
      [ CEO Agent ]（负责任务总览与最终拍板）
           │
    ┌──────┼──────┐
[ 技术主管 ]   [ 市场主管 ]
    │              │
[ 开发 A ]   [ 文案/活动 ]
```

层级模式的优点是天然对齐组织结构、易于加约束；缺点是一旦层级多，错误会在传递中逐级放大，且低层 Agent 缺乏全局视野。

### 3.5 P2P 对等模式（Peer-to-Peer）

所有 Agent 地位完全对等，通过一个共享的消息总线（Message Bus / Blackboard）自由发布和订阅消息，A 的任务结果可以成为 B 的输入，无需中央调度。类似微服务架构里的消息队列 + 事件驱动。

```
        ┌─────────── 共享消息总线（黑板消息队列）───────────┐
        │                                                    │
   [ Agent A ]   [ Agent B ]   [ Agent C ]      [ Agent D ]
   （发布）      （订阅 A）     （订阅 B）        （订阅 C）
```

这种模式扩展性最高，适合大规模协作；缺点是流程不受控、难以保证任务的确定性，需要靠超时、轮次限制和中间状态持久化防止系统乱掉。LangChain 的 Multi-Agent 教程演示了这类消息传递思路。

## 四、核心概念对比：主流多智能体框架横向对比

| 框架 | 组织/调度方式 | 角色模型 / 图模型实现 | 适合场景 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| **AutoGen**（微软） | 对话驱动：Agent 之间直接对话，可人工介入 | ConversableAgent 角色，支持 GroupChat + Manager 做对话管理 | 需要人工参与的复杂交互、编程类任务 | 灵活、支持人类 in-the-loop、生态成熟 | 上手曲线稍陡、对话流程难精准控制 |
| **CrewAI** | 流程驱动：任务（Task）+ 角色（Agent）+ Crew，支持顺序 / 层级流程 | 显式定义 role/backstory/goal，Task 之间显式传递上下文 | 内容生产、调研类流水线 | 声明式、代码量小、易上手 | 协作灵活性较低，复杂自适应场景受限 |
| **MetaGPT** | SOP 驱动：模拟软件公司，按标准流程（需求→设计→编码→测试）流水线 | 角色即状态机（产品经理/架构师/工程师），产出物为结构化文档 | 软件工程、大型项目自动开发 | 任务拆解质量高、产出结构化 | 对简单任务过重、Token 消耗大 |
| **LangGraph** | 图驱动：把多 Agent 协作建模为有状态图（节点=Agent，边=转移） | StateGraph 显式建模状态与边，支持循环、条件跳转、并行分支 | 需要精确控制流程与状态的生产级应用 | 控制力最强、可持久化（checkpoint） | 相对底层，样板代码多 |
| **OpenAI Swarm** | 极简 Agent 编排：Agent 可注册 tool，通过 handoff 把会话交接给其它 Agent | 每次只运行一个 Agent，handoff 后上下文移交，无状态、透明 | 轻量原型、路由与分工明确的服务式 Agent | 极简、代码透明、易理解 | 实验性，不适合生产与复杂状态 |

选择建议：想要"快速出效果"用 CrewAI；要精确控制流程图用 LangGraph；要做"多角色对话 + 人类参与"用 AutoGen；要"软件工程级产出"用 MetaGPT；想搞懂多 Agent 最朴素的交接逻辑，先读 Swarm。

## 五、Agent 之间通信与共享

多 Agent 只有在能"共享信息"时才有协作意义，常见三个共享维度：

1. **共享记忆（Shared Memory）**：多个 Agent 共用一个长期记忆库（向量库）。任何 Agent 写入的经验，其它 Agent 可检索复用，避免了重复犯错。实现上通常用一个全局 `messages` 列表或向量数据库作为黑板。
2. **消息队列 / 消息总线（Message Bus）**：Agent 之间通过队列收发结构化消息（任务、结果、事件）。LangGraph 的 Channel、AutoGen 的 GroupChat、以及独立的 Redis/MQ 消息队列都可承担此职责。
3. **工具共享（Tool Sharing）**：公共工具池（搜索、计算器、数据库连接）注册在协作层，任何 Agent 都能按需调用，避免每个 Agent 重复实现工具。注意要为共享工具加"并发安全"与"权限控制"。

## 六、代码实践：CrewAI 最小可运行示例（顺序流水线）

以 CrewAI 为例演示最简单的双 Agent 协作：一个"研究员"产出要点，一个"写手"基于要点成文。

依赖安装：

```bash
pip install crewai crewai-tools openai
```

> 需要设置环境变量 `OPENAI_API_KEY`（若使用 OpenAI 兼容接口，也可配置 `OPENAI_BASE_URL` 指向其它服务）。

最小可跑代码：

```python
from crewai import Agent, Task, Crew, Process

# 1. 定义两个角色 Agent
researcher = Agent(
    role="行业研究员",
    goal="深入研究目标行业并输出结构化的调研要点",
    backstory="你是一位有十年经验的行业研究员，擅长信息整合与洞察提炼。",
    verbose=True,
)

writer = Agent(
    role="内容写手",
    goal="基于调研要点撰写一篇通俗易懂的中文科普长文",
    backstory="你是一位擅长把专业内容讲得通俗易懂的写作者。",
    verbose=True,
)

# 2. 定义两个任务，分别绑定到对应 Agent
research_task = Task(
    description="调研 2025 年大语言模型多智能体协作领域的最新进展，输出 5 个核心要点。",
    agent=researcher,
    expected_output="5 个核心要点，每个要点包含一句话结论与支撑论据。",
)

write_task = Task(
    description="根据行业研究员的要点，撰写一篇 800 字的中文科普文章。",
    agent=writer,
    expected_output="一篇完整的中文科普文章，包含标题与正文。",
)

# 3. 组装 Crew：顺序执行，研究结果自动传给写手
crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.sequential,
)

# 4. 启动
result = crew.kickoff()
print(result)
```

运行逻辑：CrewAI 先在内部执行 research_task，把结果写入共享上下文；随后 write_task 的 description 里引用的前序输出会自动注入写手的上下文，写手据此成文。如果想并行，CrewAI 还支持 `Process.hierarchical`（由 Manager Agent 分配任务）以及通过 `start_task_ids`/`async_execution` 实现并行分支。

## 七、设计考量、常见坑与最佳实践

### 7.1 成本与 Token 消耗

多 Agent 会放大调用成本：辩论几轮就是几倍的模型调用。建议：能单 Agent 解决就不上多 Agent；复用同一批 Agent 实例、批量处理请求；市区分"贵模型（规划/总结）"与"便宜模型（子任务执行）"；用缓存/共享记忆减少重复计算。

### 7.2 错误传播

一个 Agent 的错误结果可能被下游当作事实继续加工，形成错误放大。对策：关键环节加验证 Agent 或质量门禁（check）、保留原始证据供人工审查、设置最大重试/兜底路径。

### 7.3 角色一致性

Agent 角色定义越清晰，输出越稳定。建议把 role/goal/backstory 写得具体，并在每个任务里强调"你是谁、要为谁、产出什么格式"，防止 Agent 跑偏去执行不属于自己的职责。

### 7.4 任务拆解分工

好的拆解满足：子任务彼此尽可能解耦（减少 Agent 间依赖）、粒度适中（每个子任务让一个 Agent 一次能完成）、有明确验收标准（expected_output）。拆得过大则退回单 Agent；拆得过碎则通信开销大于收益。

### 7.5 常见坑

- **死循环**：协商/辩论模式不设最大轮次 → 必须加轮次上限。
- **上下文漂移**：Agent 间传递完整聊天记录导致上下文爆炸 → 只传递结构化摘要/关键结果。
- **信息孤岛**：Agent 之间不共享记忆，重复犯错 → 引入共享记忆库。
- **幻觉互相传染**：多个 Agent 互相引用编造的内容 → 要求输出引用来源、加入验证 Agent。
- **一把梭**：不管任务复杂度都上多 Agent → 先评估单 Agent 是否能完成。

## 八、小结

多智能体协作的核心价值在于"把复杂任务拆解给多个专业 Agent，再通过可控的协作机制组织起来"，它解决了单 Agent 在上下文、角色一致性、并行效率与自我纠错上的瓶颈。五种主流模式（编排者、协商、辩论、层级、P2P）各有适用边界：需要精细控制用 Orchestrator 或图；需要互动对话用协商/辩论；需要企业级分工用层级；需要大规模松耦合用 P2P。框架选择上，CrewAI 适合快速原型，LangGraph 适合生产级流程控制，AutoGen 适合人类参与的多角色对话，MetaGPT 适合软件工程流水线。最后记住：多 Agent 不是越多越好，成本、错误传播与角色一致性都是必须纳入设计的约束。
